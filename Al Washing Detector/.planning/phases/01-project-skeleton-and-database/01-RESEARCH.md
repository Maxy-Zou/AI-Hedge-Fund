## Summary

Phase 1 establishes the foundation: an installable Python package (`ai_washer`) with a PostgreSQL database layer using append-only schema, dual timestamps, and monthly range partitioning. The package must be pip-installable with CLI entry points and must load all configuration from YAML/env files via Pydantic validation.

The technology choices are locked and well-verified: uv for package management, SQLAlchemy 2.0 with psycopg3 (sync) for the ORM, Alembic for migrations, Pydantic + pydantic-settings for config, and Typer for CLI. The primary technical complexity lies in (a) correctly modeling PostgreSQL range-partitioned tables in SQLAlchemy 2.0 declarative style while working around Alembic's limited partition autogenerate support, and (b) implementing the dual-timestamp (as_of_date, observed_date) pattern consistently across all financial data tables.

**Primary recommendation:** Use `uv init --package` to scaffold the src layout, write Alembic migrations manually (not autogenerated) for partitioned tables, and split configuration into two Pydantic settings classes: one for secrets/env (`.env` + environment variables) and one for scoring/business config (`config/scoring.yaml`).

### Pattern 1: Dual-Timestamp Mixin for Append-Only Tables

**What:** A SQLAlchemy mixin class that adds `as_of_date` and `observed_date` to any model. All financial data tables inherit this mixin.

**When to use:** Every table that stores financial data (daily_scores, signal_details, and any future raw data tables).

**Example:**
```python
# Source: Locked decision D-08 + PITFALLS.md Pitfall 2
import uuid
from datetime import date, datetime
from sqlalchemy import Date, DateTime, func
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column

class Base(DeclarativeBase):
    pass

class DualTimestampMixin:
    """Mixin for append-only financial data tables.

    as_of_date: when the underlying event/data was true (business date)
    observed_date: when our system first collected/observed it
    """
    as_of_date: Mapped[date] = mapped_column(Date, nullable=False)
    observed_date: Mapped[date] = mapped_column(
        Date, nullable=False, server_default=func.current_date()
    )

class AppendOnlyMixin(DualTimestampMixin):
    """Extends DualTimestampMixin with UUID PK and created_at."""
    id: Mapped[uuid.UUID] = mapped_column(
        primary_key=True, default=uuid.uuid4
    )
    created_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True), nullable=False,
        server_default=func.now()
    )
```

### Pattern 2: Partitioned Table with SQLAlchemy __table_args__

**What:** Declare range-partitioned tables using `postgresql_partition_by` in `__table_args__`. Create actual partitions in Alembic migrations using raw SQL.

**When to use:** `daily_scores` table (locked decision D-06). Optionally `signal_details` if data volume warrants it.

**Example:**
```python
# Source: SQLAlchemy 2.0 docs + Alembic #539 workaround
from sqlalchemy import SmallInteger, ForeignKey, Index
from sqlalchemy.dialects.postgresql import JSONB

class DailyScore(AppendOnlyMixin, Base):
    __tablename__ = "daily_scores"
    __table_args__ = (
        # scored_at must be part of PK for partitioning
        Index("ix_daily_scores_company_scored",
              "company_id", "scored_at"),
        {"postgresql_partition_by": "RANGE (scored_at)"},
    )

    # Override id to include scored_at in composite PK
    id: Mapped[uuid.UUID] = mapped_column(primary_key=True, default=uuid.uuid4)
    scored_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True), nullable=False, primary_key=True
    )
    company_id: Mapped[uuid.UUID] = mapped_column(
        ForeignKey("companies.id"), nullable=False
    )
    composite_score: Mapped[int] = mapped_column(
        SmallInteger, nullable=False
    )
    signal_breakdown: Mapped[dict] = mapped_column(JSONB, nullable=False)
    confidence: Mapped[float] = mapped_column(nullable=False)
    weights_used: Mapped[dict] = mapped_column(JSONB, nullable=False)
    run_id: Mapped[uuid.UUID] = mapped_column(nullable=False)
```

**CRITICAL: Partition PK constraint.** PostgreSQL requires the partition key column to be part of the primary key. UUID alone cannot be the PK on a partitioned table. Use composite PK `(id, scored_at)`.

### Pattern 3: Pydantic Dual-Source Configuration

**What:** Two settings classes -- one for secrets (env/dotenv), one for business config (YAML). Layered with env vars overriding YAML.

**When to use:** All configuration loading at application startup.

**Example:**

```python
from pydantic_settings import BaseSettings, SettingsConfigDict

class AppSettings(BaseSettings):

class SignalWeights(BaseModel):
```

### Pattern 4: Alembic env.py Reading DATABASE_URL from Environment

**What:** Configure Alembic's env.py to read the database URL from the environment (via the shared Pydantic settings) rather than hardcoding in alembic.ini.

**When to use:** Always. Never put credentials in alembic.ini.

**Example:**
```python
# Source: Alembic 1.18.4 docs + pydantic-settings integration
# migrations/env.py
import os
from alembic import context
from sqlalchemy import engine_from_config, pool
from ai_washer.db.base import Base

def get_url() -> str:
    return os.environ.get(
        "AI_WASHER_DATABASE_URL",
        "postgresql+psycopg://localhost:5432/ai_washer"
    )

def run_migrations_online() -> None:
    configuration = config.get_section(config.config_ini_section, {})
    configuration["sqlalchemy.url"] = get_url()
    connectable = engine_from_config(
        configuration,
        prefix="sqlalchemy.",
        poolclass=pool.NullPool,
    )
    with connectable.connect() as connection:
        context.configure(
            connection=connection,
            target_metadata=Base.metadata,
        )
        with context.begin_transaction():
            context.run_migrations()
```

### Anti-Patterns to Avoid

- **Autogenerating migrations for partitioned tables:** Alembic's autogenerate does not understand PostgreSQL partitions. It will attempt to re-create the parent table and drop all partitions on subsequent runs. Write partition-related DDL manually using `op.execute()`.
- **UUID-only primary key on partitioned tables:** PostgreSQL requires the partition key to be part of the primary key. A partitioned table with PK `(id UUID)` will fail. Must use composite PK `(id, partition_column)`.
- **Using `postgresql+psycopg2://` URLs with psycopg3:** The psycopg3 driver uses `postgresql+psycopg://` (no "2"). Using the psycopg2 URL format will import the wrong (or missing) driver.
- **Hardcoding DATABASE_URL in alembic.ini:** Violates 12-factor. Read from environment in env.py.
- **Mutable model patterns:** No `update()` methods on append-only models. Repository layer should only expose `insert()` and `query()` operations for financial data.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| YAML config loading | Custom YAML parser + dict merging | `pydantic-settings[yaml]` YamlConfigSettingsSource | Handles type coercion, validation, env override, nested models. Custom YAML parsing always misses edge cases. |
| Database migrations | Raw SQL scripts or custom migration runner | Alembic | Version tracking, transactional rollback, dependency ordering, autogenerate for non-partitioned tables. |
| CLI argument parsing | argparse or manual sys.argv parsing | Typer | Type-hint derived, auto-help, auto-completion, sub-commands. |
| UUID generation | Custom ID schemes | Python `uuid.uuid4()` + PostgreSQL `gen_random_uuid()` | Globally unique, no coordination needed, standard across all tools. |
| Connection pooling | Manual connection management | SQLAlchemy Engine (built-in pool) | Handles pool sizing, recycling, overflow. Manual connection management leaks connections. |
| Structured logging setup | Custom JSON formatter on stdlib logging | structlog | Processor pipeline, bound loggers, context propagation. 5 lines of config vs 50 lines of custom code. |

**Key insight:** Phase 1 is infrastructure. Every component has a mature, standard solution. Custom solutions here create maintenance burden for all subsequent phases.

## Common Pitfalls

### Pitfall 1: Partition Key Not in Primary Key

**What goes wrong:** Declaring `id: UUID` as the sole primary key on a table with `postgresql_partition_by='RANGE (scored_at)'` causes PostgreSQL to reject the table creation: "unique constraint on partitioned table must include all partitioning columns."

**Why it happens:** PostgreSQL enforces that the partition key is part of every unique constraint (including PK) so it can route inserts to the correct partition without scanning all partitions for uniqueness.

**How to avoid:** Use composite primary key `(id, scored_at)` on all partitioned tables. The UUID ensures global uniqueness; scored_at enables partition routing.

**Warning signs:** `CREATE TABLE` or `Alembic upgrade` fails with a constraint error mentioning "partitioning columns."

### Pitfall 2: Alembic Autogenerate + Partitions = Broken Migrations

**What goes wrong:** Running `alembic revision --autogenerate` on a database with partitioned tables produces migrations that (a) try to recreate the parent table, (b) try to drop all partition children, and (c) duplicate index creation.

**Why it happens:** Alembic's autogenerate does not distinguish partitions from regular tables. It sees the parent table reflected differently and treats partitions as unknown tables to be dropped.

**How to avoid:** Write partition-related migrations manually. Use `include_object` hook in `env.py` to filter partition tables from autogenerate. Only use autogenerate for non-partitioned tables.

**Warning signs:** Autogenerated migration contains `op.drop_table('daily_scores_2026_01')` or `op.create_table('daily_scores', ...)` when the table already exists.

### Pitfall 3: psycopg2 vs psycopg3 URL Confusion

**What goes wrong:** Using `postgresql://` or `postgresql+psycopg2://` in the connection URL when psycopg3 is installed (but psycopg2 is not). SQLAlchemy defaults to psycopg2 for bare `postgresql://` URLs.

**Why it happens:** Most tutorials and Stack Overflow answers use psycopg2 URLs. psycopg3 requires explicit `postgresql+psycopg://` dialect.

**How to avoid:** Always use `postgresql+psycopg://` in all connection URLs. Validate in the Pydantic settings model that DATABASE_URL contains the correct dialect.

**Warning signs:** `ModuleNotFoundError: No module named 'psycopg2'` at startup despite having psycopg (v3) installed.

### Pitfall 4: Missing scored_at in Foreign Key References

**What goes wrong:** Other tables referencing `daily_scores(id)` with a single-column FK fail because the PK is composite `(id, scored_at)`.

**Why it happens:** When the PK changes to composite for partitioning, all FK references must also be composite -- or FKs must be dropped entirely. PostgreSQL does not support foreign keys referencing partitioned tables (only from partitioned tables to non-partitioned tables).

**How to avoid:** Design the schema knowing that `daily_scores` and `signal_details` are partitioned. Other tables should reference `companies(id)` (non-partitioned) and store `run_id` for traceability, not FK to score tables. Use `run_id` as a logical (not enforced) reference.

**Warning signs:** `CREATE TABLE ... REFERENCES daily_scores(id)` fails with "cannot reference partitioned table."

### Pitfall 5: YAML Config Not Found in Installed Package

**What goes wrong:** `config/scoring.yaml` exists in the repo root but is not included when the package is pip-installed. The settings class fails to find the YAML file at runtime.

**Why it happens:** Python packages only install files under `src/`. The `config/` directory at project root is not part of the package.

**How to avoid:** Either (a) use `importlib.resources` to bundle default config inside the package and allow override via an env var pointing to an external YAML path, or (b) always require the YAML path to be specified via environment variable `AI_WASHER_SCORING_CONFIG`. Option (b) is simpler and more 12-factor compliant.

**Warning signs:** `FileNotFoundError: config/scoring.yaml` after `pip install -e .` from a different working directory.

### Alembic Migration with Manual Partition Creation

```python
# Source: Alembic 1.18.4 docs + PostgreSQL partition docs
"""create initial schema

Revision ID: 001
"""
from alembic import op
import sqlalchemy as sa
from sqlalchemy.dialects.postgresql import JSONB, UUID

def upgrade() -> None:
    # companies (non-partitioned)
    op.create_table(
        "companies",
        sa.Column("id", UUID(as_uuid=True), primary_key=True),
        sa.Column("ticker", sa.String(10), unique=True, nullable=False),
        sa.Column("name", sa.Text, nullable=False),
        sa.Column("cik", sa.String(10)),
        sa.Column("market_cap_cents", sa.BigInteger),
        sa.Column("sector", sa.Text),
        sa.Column("created_at", sa.DateTime(timezone=True),
                  server_default=sa.func.now(), nullable=False),
        sa.Column("metadata", JSONB, server_default="{}",
                  nullable=False),
    )

    # daily_scores (range-partitioned by scored_at)
    op.execute("""
        CREATE TABLE daily_scores (
            id UUID NOT NULL DEFAULT gen_random_uuid(),
            scored_at TIMESTAMPTZ NOT NULL,
            company_id UUID NOT NULL REFERENCES companies(id),
            as_of_date DATE NOT NULL,
            observed_date DATE NOT NULL DEFAULT CURRENT_DATE,
            composite_score SMALLINT NOT NULL
                CHECK (composite_score BETWEEN 0 AND 100),
            signal_breakdown JSONB NOT NULL,
            confidence REAL NOT NULL
                CHECK (confidence BETWEEN 0.0 AND 1.0),
            weights_used JSONB NOT NULL,
            run_id UUID NOT NULL,
            created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
            PRIMARY KEY (id, scored_at)
        ) PARTITION BY RANGE (scored_at)
    """)

    # Create initial monthly partitions
    op.execute("""
        CREATE TABLE daily_scores_2026_03 PARTITION OF daily_scores
            FOR VALUES FROM ('2026-03-01') TO ('2026-04-01')
    """)
    op.execute("""
        CREATE TABLE daily_scores_2026_04 PARTITION OF daily_scores
            FOR VALUES FROM ('2026-04-01') TO ('2026-05-01')
    """)

    # signal_details (range-partitioned by scored_at)
    op.execute("""
        CREATE TABLE signal_details (
            id UUID NOT NULL DEFAULT gen_random_uuid(),
            scored_at TIMESTAMPTZ NOT NULL,
            company_id UUID NOT NULL REFERENCES companies(id),
            signal_type TEXT NOT NULL,
            score SMALLINT NOT NULL CHECK (score BETWEEN 0 AND 100),
            as_of_date DATE NOT NULL,
            observed_date DATE NOT NULL DEFAULT CURRENT_DATE,
            evidence JSONB NOT NULL,
            model_version TEXT NOT NULL,
            run_id UUID NOT NULL,
            created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
            PRIMARY KEY (id, scored_at)
        ) PARTITION BY RANGE (scored_at)
    """)

    # Create initial monthly partitions for signal_details
    op.execute("""
        CREATE TABLE signal_details_2026_03 PARTITION OF signal_details
            FOR VALUES FROM ('2026-03-01') TO ('2026-04-01')
    """)
    op.execute("""
        CREATE TABLE signal_details_2026_04 PARTITION OF signal_details
            FOR VALUES FROM ('2026-04-01') TO ('2026-05-01')
    """)

    # pipeline_runs (non-partitioned, low volume)
    op.create_table(
        "pipeline_runs",
        sa.Column("id", UUID(as_uuid=True), primary_key=True),
        sa.Column("started_at", sa.DateTime(timezone=True),
                  server_default=sa.func.now(), nullable=False),
        sa.Column("completed_at", sa.DateTime(timezone=True)),
        sa.Column("status", sa.Text, nullable=False,
                  server_default="running"),

                  server_default="{}"),
        sa.Column("companies_processed", sa.Integer, default=0),
        sa.Column("errors", JSONB, server_default="[]"),
    )

    # Indexes on partitioned tables (created on parent, inherited by partitions)
    op.execute("""
        CREATE INDEX ix_daily_scores_company_scored
            ON daily_scores (company_id, scored_at DESC)
    """)
    op.execute("""
        CREATE INDEX ix_signal_details_company_type_scored
            ON signal_details (company_id, signal_type, scored_at DESC)
    """)

def downgrade() -> None:

    op.execute("DROP TABLE IF EXISTS daily_scores CASCADE")
    op.drop_table("pipeline_runs")
    op.drop_table("companies")
```

## State of the Art

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|--------------|--------|
| psycopg2 + `postgresql://` | psycopg3 + `postgresql+psycopg://` | SQLAlchemy 2.0 (2023) | Must use explicit dialect. Default bare `postgresql://` still tries psycopg2. |
| setup.py / setup.cfg | pyproject.toml (PEP 621) | 2022-2024 | Single file for all metadata. uv + hatchling + setuptools all support it. |
| pip + virtualenv + pip-tools | uv (single tool) | 2024-2026 | 10-100x faster. Replaces 4+ tools. Standard for new projects. |
| black + flake8 + isort | ruff (single tool) | 2023-2026 | 10-100x faster. Single config. Replaces 3+ tools. |
| SQLAlchemy 1.x Column() | SQLAlchemy 2.0 mapped_column() + Mapped[] | 2023 | Type-safe, IDE-friendly. 1.x style still works but is legacy. |
| poetry.lock | uv.lock | 2024-2026 | uv lockfiles are faster to resolve and cross-platform. |

**Deprecated/outdated:**
- `psycopg2-binary`: Use `psycopg[binary]` (v3) instead. psycopg2 is in maintenance mode.
- `setup.py`: No longer needed with PEP 621 pyproject.toml.
- `black`/`flake8`/`isort` as separate tools: ruff replaces all three.

## Open Questions

1. **Partition creation automation**
   - What we know: Alembic migrations can create initial partitions. New monthly partitions will be needed over time.
   - What's unclear: Should partition creation be a cron job, a CLI command, or part of the scoring pipeline?
   - Recommendation: For Phase 1, create 6 months of partitions in the initial migration. Add a CLI command `ai-washer create-partitions --months-ahead 6` that can be run manually or via cron. Full automation deferred to Phase 10.

2. **Alembic include_object filter for partitions**
   - What we know: The `include_object` hook can filter partition tables from autogenerate.
   - What's unclear: Exact regex pattern for detecting partition names vs regular tables.
   - Recommendation: Use naming convention `{parent_table}_{YYYY}_{MM}` and filter with regex in `include_object`. Document the convention.

3. **Docker requirement for integration tests**
   - What we know: Docker is available on this machine. testcontainers requires Docker.
   - What's unclear: Whether CI/CD environment also has Docker available.
   - Recommendation: Use testcontainers for local integration tests. Provide `pytest.ini` marker to skip DB tests when Docker is not available (`@pytest.mark.integration`).
