# v1.1 Plan — Paper Trading + Promotion Gate

**Status:** Drafted 2026-04-24. Not yet spun up as a GSD milestone.
**Trigger to promote to `/gsd-new-milestone`:** v1.0 UAT items closed, or user explicitly says "start paper trading".

## Core principle

Build the track-record loop on the signals v1.0 already produces. Do **not** add academic-paper ingestion to the pipeline — that is a separate side project (see Parking Lot). The v1.1 goal is: prove the v1.0 pipeline produces tradable signals, on a real clock, with a compliance-grade record.

## Why this, why now

- **YC / LP credibility gap.** Without a track record (even paper), the multi-agent research system has no external proof. Paper trading is the cheapest form of proof.
- **FINSABER problem.** Backtests on LLM strategies are unreliable; only forward paper trading on live data produces a credible record.
- **Already on the v1.1 list.** `.planning/PROJECT.md` → Active → "Paper trading integration to generate a track record from signals".

## Scope — IN

1. Paper-trading execution layer (Alpaca paper account, free)
2. Append-only `paper_trades` + `paper_fills` tables
3. Daily mark-to-market job + per-signal attribution
4. Promotion gate with SHA-pinned thresholds (same compliance pattern as `risk_policy_sha`)
5. Track-record report (CLI, JSON + markdown, YC/LP-shareable)

## Scope — OUT (v1.1)

- Literature mining / auto-strategy discovery from arXiv/SSRN
- Live capital or real broker
- Portfolio optimization on ranked signals
- Web/TUI reviewer UI (defer to v1.2+)

### Phase B — Track-record storage

### Phase C — Mark-to-market & attribution
- [ ] Daily EOD job: pull fills + current adjusted-close → compute P&L

### Phase D — Promotion gate
- [ ] `config/promotion_policy.yaml`: N paper-days, min Sharpe, max DD, min hit-rate, min sample size
- [ ] `promotion_policy_sha` computed exactly like `risk_policy_sha` (Phase 6 pattern)
- [ ] Gate function: `signal → {paper-only, eligible-for-live, rejected}`
- [ ] `promotion_policy_sha` joins the audit chain — round-trips through state, column, payload

### Phase E — Reporting
- [ ] CLI: `render_track_record --since YYYY-MM-DD --format {json,md}`
- [ ] Markdown output is LP/YC-shareable (clean, no internal paths)
- [ ] Langfuse hook: track-record generation emits a trace for cost correlation

## Non-negotiables (carried from v1.0)

- **Tool-first.** LLM never computes P&L, attribution, position size, or promotion decision. Deterministic Python owns every number.
- **Append-only.** No row is ever updated. Review/promotion decisions create new rows.
- **Temporal correctness.** Every query filters `as_of_date <= target`. FUTUREX regression seeds extended to new tables.
- **Compliance audit chain.** `risk_policy_sha` + `review_policy_sha` + `promotion_policy_sha` all round-trip.

## Parking lot (explicitly deferred)

- **arXiv / SSRN weekly digest.** Side project, not pipeline. At most: cron → Haiku summarization → Slack channel for human (Max) to read. Never wired into agents. Rationale: Hou/Xue/Zhang (2020) replicated 452 anomalies, ~64% failed — auto-extracting strategies from papers would pollute signal with decayed anomalies.
- **Strategy auto-extraction from papers.** Probably never. Replication crisis makes it low-EV. Revisit only if a clean academic replication workflow exists.
- **Reviewer UI (web/TUI).** v1.2+.
- **Portfolio optimization on SIG-02 rank.** v1.2+.
- **Real-broker execution.** Only after promotion gate has cleared on paper for a documented window.

## Why no paper-ingestion in v1.1

Three reasons, in case this question comes back up:

1. **Positioning.** The v1.0 story is "multi-agent research on filings". Adding "we also read papers and trade them" dilutes a tight pitch.
2. **Signal quality.** Published anomalies decay. An LLM that auto-extracts strategies from arXiv will surface mostly garbage without heavy human filtering.
3. **Sequencing.** Build the track-record loop first on signals we already produce, *then* decide if literature mining is worth adding. The track record is the credential; paper ingestion is a feature.
